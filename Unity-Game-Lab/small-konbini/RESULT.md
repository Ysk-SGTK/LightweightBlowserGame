## 2026-10-06 追加依頼：期待値シミュレーションと2人目の店員

今回追加した経営要素は開店前の予測と毎日の追加店員選択のみ。以降の旧セクションは以前の改修履歴として保持する。変更前は `evidence/baseline-v3/`。

### 期待値の算出・保存

`ShopForecast.cs` が現在の天気、価格、在庫＋注文、棚の商品・容量・スロット、店員数をコピーし、実際の `StoreSimulation` を別の固定乱数系列24本で実行する。客の入店、歩行、購入判断、棚欠品、レジ、補充、閉店まで同じ処理を通す。見た目だけの売上加算や、2人時の直接販売倍率は追加していない。

- 商品別：予定在庫、販売数・売上・粗利益・残在庫の範囲、売切リスク、廃棄リスク。予測の残在庫は廃棄直前の余り。日次実績の残在庫は従来どおり廃棄後。
- 合計：予想売上、既知の仕入支出、粗利益、廃棄損失、人件費、電気代、利益、棚での機会損失。利益は各試行内で会計し、その結果から範囲を作る。別々の指標の下限/上限を引き算した架空の利益幅ではない。
- 範囲は24試行の約10〜90パーセンタイル（整数インデックスへ丸めた中央約80%）。平均も記録する。リスクは欠品/廃棄を観測した試行の割合：60%以上は高、20%以上は中、それ未満は低。非生鮮の廃棄は対象外。
- 実需要の来客数の±10%変動、購入確率、商品候補と歩速のランダム性を維持。予測は本番のRandomを消費・参照せず、24個の独立した固定seedで概算する。同じ設定を開き直しても予測を引き直さない。確率区間の保証や最適解ではない。
- 天気・仕入・価格・棚割り当て・容量・配置・店員数の変更時だけ再計算するキャッシュ。設定パネルだけで表示する。予算オーバーの設定も概算可能だが、従来の仕入予算チェックで開店は拒否する。
- 開店時の予測をDayReportに固定保存。閉店後の5商品一覧で販売数・売上の実績と予測を上下に表示する。翌日の設定変更・前日結果の再表示で過去の予測は変化しない。
- 7日間結果に人件費合計、2人使用日数、予想利益合計レンジ、実利益、予測平均との差を追加。合計レンジは日別の下限/上限の単純合計で、7日間全体の80%区間を意味しない。差は実利益−各日の予測平均の合計。

### 店員と会計

初期は1人。仕入れ・価格パネルの1人/2人ボタンで当日の営業前だけ選択する。3人目、能力差、レベル、シフト等はない。1人時は従来のレジ優先と補充を同じ人物が担当。2人時は緑の店員がレジ、青の追加店員が倉庫→棚への品出しを担当し、並行作業できる。二重補充はせず、運搬中の在庫も整合検査へ含める。追加店員は実GameObjectで表示し、箱の持ち運び・補充・待機を画面で確認できる。

1人目は600円/日、2人目は追加1,500円/日、2人合計2,100円/日。閉店時に支払い、DayReportに当日の店員数・人件費を固定する。利益＝売上−販売商品の原価−廃棄商品の原価−電気代−人件費。「仕入額」は当日の仕入支出であり、利益から再度全額を引かない。持越し在庫を資産として残す従来会計を維持し、cash＋残在庫原価−開始資金＝累計利益を照合した。購入済みの廃棄原価を二重に控除しない。

### 分析コメント

機会損失と廃棄前の余り（廃棄数または残在庫）が併存する場合は、補充遅れの可能性を最優先。機会損失があり廃棄・残在庫とも0なら仕入れ不足。高価格・拒否3件以上・基本需要の半分未満の販売・余りありなら価格の可能性。その後に廃棄過多、欠品、残在庫が多い、販売あり/なしを判定する。在庫を用意していない商品の販売0を価格のせいだけにしない。会計前の客が商品を持っていたことを、閉店後の未販売在庫として扱わない。

追加店員のコメントは同じ設定で1人だった場合の24試行の概算との比較。実際に同じ日の1人営業を同時観測した因果効果ではないため、「概算」「可能性」と表示する。実利益増かつ欠品減なら貢献の可能性、概算からの売上増が追加賃金未満なら人件費負担の可能性を表示する。

画面外の歩道 → 入口 → 入店 → 商品棚 → 0.4秒見る → 購入判断 → 商品を持つ → レジ列 → 会計 → 入口 → 歩道へ退店。

在庫なし・陳列なしなら「ない…」、価格拒否なら「高いな…」を短く出して退店。購入判断成功時は棚在庫を1減らし、客が商品を持つ。**この時点では売上・現金・販売個数を加算しない**。店員による会計完了で一度だけ加算し、レジ付近に+金額を表示する。商品を取った客が裏の乱数計算とは無関係に歩いている構造ではない。

客は最大8人、レジ列は最大4人。列満員時は商品を持った客が手前で待つ。複雑な衝突・NavMesh・経路探索はなし。固定通路を経由するWaypoint移動。服の色・サイズ・移動速度が少し異なる。

### 店員

1人のみ。列があればレジへ戻り、先頭客を0.22秒で会計する。列がなければ、容量の約1/3以下の棚から補充対象を選ぶ。

倉庫へ歩く → 商品用意0.35秒 → 商品箱を持って棚へ歩く → 補充0.55秒 → レジへ戻る。

開始済みの品出しは途中キャンセルしないので、その間にレジ列ができる。移動速度は5 world units/営業秒。移動時間に加えて作業時間がかかる。倉庫から離れた棚では移動が長くなる。

### 在庫

- ShopModel.stock: 未販売の商品総数（倉庫 + 棚 + 未会計客の手持ち + 店員の運搬分）。
- StoreSimulation.warehouse: バックヤード在庫。
- StoreShelf.stock: 陳列在庫。棚ごとに容量を持つ。
- 客のcarrying: 棚から取ったが未会計の商品1個。
- 店員のcarried / carriedProduct: 倉庫から棚へ運搬中の商品。

棚が空なら倉庫に在庫があっても購入できず、機会損失になる。各フレームの在庫一致チェックで、運搬・予約中を含め総数が一致することを検証する。結果の「在庫があったのに棚で買えなかった」には倉庫・運搬中・別棚・他客の未会計分も含む。倉庫だけの補充遅延件数と混同しない。倉庫配列に実在する場合だけの欠品は別の観測カウンターで区別する。閉店は客の会計・退店と運搬完了を待つため、未会計商品を誤って廃棄・売上処理しない。閉店時に棚残数を倉庫へまとめ、生鮮だけ廃棄。開店時は仕入れ後の在庫を棚容量まで順に初期陳列する。開店前の箱表示は仕入れ予定込みのプレビューで、同商品を複数棚に置いても数量を重複使用しない。

### 棚・配置

6棚、8スロット。通常棚は容量8または10、冷蔵棚1台は容量10。通常棚は全5商品、冷蔵棚は弁当・飲料に対応。棚の選択 → 商品選択 / スロット選択。同じ商品を複数棚に配置でき、占有スロットへ置くと2棚が交換される。開店前だけ変更可能。Drag & Dropや完全自由配置はない。

客も店員も選んだ棚スロットの位置へ実際に歩く。通路を経由するため、距離が営業時間と待ち時間に直接影響する。通常棚の電気代0円、冷蔵棚300円/日。冷蔵による需要ボーナスや品質差は追加していない。

### 時間・閉店

通常速度45秒で8:00→22:00。朝(8〜11時):来店率0.7、昼(11〜14時):1.35、夕方(14〜18時):1.2、夜(18〜22時):0.8。既存需要から作った来店予定数とこの時間帯係数を使い、最大人数に達すると次の入店を待たせる。

22:00に新規入店を停止。入店できなかった予定客は、実際の来店や機会損失には数えない。店内客が全員退出すると閉店。ゲーム速度は×1 / ×2 / ×4で、時計・移動・見る時間・品出し・レジをまとめて同じ倍率にする。閉店後の待ちを含め通常の1日は約50〜60秒になる。閉店結果→翌日→天気/仕入れ/棚/価格の変更→開店、7日目→最終結果→もう一度、を維持。

## 電気代・利益

当日粗利益 = 売上 − 売れた商品の原価。
当日最終利益 = 粗利益 − 廃棄原価 − 電気代。
現金 = 前日現金 − 仕入れ額 + 会計済み売上 − 電気代。

廃棄時に原価を再度現金から引かない。持越し在庫は販売されるまで費用化しない。期末現金 + 期末在庫原価 − 初期30,000円 = 累計利益。冷蔵棚1台なので7日の電気代は2,100円。

## 1営業日を眺めた評価・現時点の弱点

- 店を眺める意味: 客が棚を見て商品箱を持ち、店員が箱を運び、補充中に列が延びる。数字の一覧を読まなくても複数の出来事を観測できた。ダッシュボードの店舗図から、店舗内の活動が結果を作る画面へ変わっていると判断する。
- 売れ行き: 商品の手持ちとレジの+金額で購入/会計を識別できた。棚の商品箱も減少し、品出しで増えた。ただし買う客と退店客が入口付近で重なることがある。
- 在庫不足: 空棚が見え、小さな「空っぽ」と客の「ない…」で足りないことが分かる。箱量は0〜8個の概略表示なので、数字を見ずに正確な個数までは分からない。
- 運営感: エプロンの店員が倉庫と棚を往復し、レジ待ちが発生した。通常速度で45秒間の営業時間と残客処理を実際に観測した。時計も進み、営業の始まりと終わりが識別できた。

まだゲームらしく見えない/弱い部分:

- 人物と棚はPrimitive。歩行は滑るようなWaypoint移動で、手足の本格アニメーションや会計の手渡しはない。レジ処理は店員の状態と金額表示が主な手掛かり。
- 道路・木・隣家は静的背景。店外に街全体の生活が動いている演出はなく、夜も照明は変わらない。
- 棚や人物のラベル・吹き出しは、混んだ場面ではまだ一部重なる。人物は小さく、複数客が同じ経路で交差する。
- 1人のレジ/補充能力が販売を制限し、従来の需要目安をそのまま仕入れると生鮮が余りやすい。前日実績の参照は結果画面を覚える必要がある。強気価格が有利な日もあり、面白さの調整は人間の試遊が必要。
- 冷蔵棚は現状、商品制約・容量・電気代だけで、冷蔵による需要や品質の差はない。極端な仕入れで資金を枯渇させた場合の専用終了画面も追加していない。

人間によるUnity GUI操作、Asset購入、ライセンス/モジュール追加、認証情報変更は不要だった。Codexが生成・Editor実行・Build・ブラウザ入力・画面観測を行った。次に必要な人間操作は実際に遊び、配置と価格の判断が楽しいかを評価すること。

次に面白さへ効きそうな改善（今回追加しない、最大3点）:

1. 朝の仕入れPanelに前日の販売・廃棄・棚欠品だけを添えて、仕入れ量の修正を助ける。
2. 営業終了時に店員の補充往復距離とレジ待ちを短く示し、棚配置を変えた効果を比較しやすくする。
3. 価格・需要・棚容量・冷蔵コストを人間の試遊で調整し、価格段階や冷蔵棚への商品配置の判断に納得できる差を作る。
